0 Bu Belge Nasıl Kullanılır

Bu bir plan; kod yazımı başlamadan önce üzerinde anlaşılması gereken şeyleri içerir. Proje Dosyası "ne ve neden"i, bu belge "nasıl ve hangi sırayla"yı anlatır.

§4–5 İskeletFaz 0 başlarken. Klasör düzeni ve bileşen adları burada sabitlenir.

Plan modu ne demek Buradaki hiçbir madde "yapıldı" değil. Her iş paketinin bir kabul ölçütü var; ölçüt yazılıyken kimse "bitti mi" diye tartışmasın diye ölçülebilir yazıldı. Tahmini süre bilinçli olarak konulmadı — ekip büyüklüğü netleşince §9'a eklenecek.

1 Değerlendirmenin Plana Yansıması

15.08.2026 tarihli gentegre_ai_projesi_degerlendirme.html belgesindeki düzeltmeler bu plana şu şekilde işlendi:

D1
"Faz 0'da önce ERP sözleşmesi çıkarılmalı"
Kabul edildi. §3 bu belgenin en uzun bölümü oldu — 10 sözleşme, örnek JSON'larla. Faz 0'ın çıktısı artık "iskelet" değil, imzalanmış sözleşmeler + iskelet.
D2
"İlk prototip Cari + Stok + Satış Faturası olmalı"
Kabul edildi. Proje Dosyası'ndaki "Faz 1 = Cari + Stok" tanımı değişti; §6'da Faz 1 artık satış faturası mini akışını da içeriyor: cari seç → stok seç → fatura kes → stok düş → cari hareket → belge no → döküm → log. ERP mimarisinin gerçek sınavı burası.
D3
"SP envanteri çıkarılmalı, P1/P2/P3 ayrılmalı"
Kabul edildi. §7 envanter çıkarma yöntemini, sınıflandırma kurallarını ve "hangi iş PG function kalır, hangisi C# transaction'a taşınır" ayrımını tanımlıyor. Envanter Faz 0'ın çıktısı — Faz 1 başlamadan elde olacak.
D4
"Listeleme PG function olabilir; kayıt işlemleri C# transaction'da yönetilmeli"
Kabul edildi ve kural hâline getirildi — §7.3. Okuma tarafı veritabanına yakın, yazma tarafı uygulama katmanında. Belge no, stok hareketi, cari hareket ve log tek transaction'da.
D5
"iframe mimarisi üretimde olmamalı"
Zaten planlıydı, artık açıkça yazıldı — §4.3. iframe yalnız mockup galerisinin tekniğidir; üretimde her ekran React route + component'tir. Bu maddeyi ihlal eden hiçbir PR birleştirilmez.
D6
Sarmalayıcı bileşen adları Gen* olsun
Kabul edildi. Proje Dosyası'ndaki Gn* öneki §5'te Gen* olarak güncellendi: GenGrid, GenForm, GenLookup, GenToolbar…
D7
"AI sağ panel/dock asistan olarak konumlanmalı, bağlamlı komutlar"
Kabul edildi. Mockup'ta zaten böyle çalışıyor (v5 dock). §3.10 AI fonksiyon sözleşmesini, §8 Faz 4'ü tanımlıyor. Bağlam (modül/ekran/seçili kayıt) her çağrıda zorunlu parametre.
Bir de plan tarafından eklenen madde Sağ tuş menüsü / araç çubuğu / komut paleti / AI fonksiyon listesi tek bir aksiyon kataloğundan üretilecek (§3.9). Bu, fatura ekranlarındaki sağ tuş prototipiyle doğrulandı ve mimarinin kalıcı bir parçası olarak plana alındı.

3 Faz 0 — ERP Sözleşmeleri

Kural Bu bölüm onaylanmadan hiçbir ekran yazılmaz. Sözleşmeler sonradan değişirse 97 ekran değişir; şimdi bir hafta tartışmak, sonra üç ay düzeltmekten ucuzdur.

3.1 Liste API sözleşmesi

Tüm listeler tek bir istek/yanıt şekline uyar. Ekrana özel uç nokta yazılmaz; yalnız kaynak adı değişir.

// POST /api/liste/{kaynak}        kaynak: stok | cari | satis-faturasi ...
{
  "sayfa": 1, "boyut": 100,
  "sirala": [ { "alan": "belgeTarihi", "yon": "desc" } ],
  "filtre": {                      // ağaç yapı — AND/OR/NOT iç içe
    "op": "and",
    "kosullar": [
      { "alan": "cariKod", "op": "esit",    "deger": "CH.000142" },
      { "alan": "tarih",   "op": "arasinda","deger": ["2026-01-01","2026-08-14"] },
      { "alan": "unvan",   "op": "icerir",  "deger": "granit" }
    ]
  },
  "grup":   [ "eFaturaDurumu" ],   // opsiyonel
  "toplam": [ "kdvHaric", "kdvDahil" ],
  "gorunum": "varsayilan"          // kaydedilmiş kolon düzeni
}
// Yanıt
{
  "satirlar": [ { "id": 114080, "belgeNo": "GNT2026000000056", "kdvDahil": "1260000.00", ... } ],
  "toplamKayit": 9412,
  "toplamlar": { "kdvHaric": "84120500.00", "kdvDahil": "100944600.00" },
  "gruplar":   [ { "anahtar": "Gönderildi", "adet": 8210 } ],
  "sure_ms": 42
}
  • Operatörler sabit listedir: esit, esitDegil, icerir, baslar, biter, buyuk, kucuk, arasinda, bos, bosDegil, icinde. Serbest SQL parçası istemciden gelmez.
  • Tutarlar string taşınır ("1260000.00") — JSON sayı tipine düşürülmez.
  • Sayfa boyutu üst sınırı 500; Excel dışa aktarımı ayrı uç noktadan akış (stream) ile.
  • Yetki filtresi (firma/şube/kullanıcı) sunucuda eklenir, istekte yer almaz.
Kabul ölçütü: Aynı sözleşmeyle stok, cari ve fatura listesi çalışıyor; istemci tarafında hiçbir ekrana özel istek gövdesi yok.

3.2 Kart (kayıt) sözleşmesi

GET    /api/kart/{kaynak}/{id}         → kayıt + satırlar + surum
POST   /api/kart/{kaynak}              → yeni kayıt
PUT    /api/kart/{kaynak}/{id}         → güncelle (surum zorunlu)
DELETE /api/kart/{kaynak}/{id}
POST   /api/kart/{kaynak}/dogrula      → kaydetmeden doğrula

{
  "id": 114080, "surum": "2026-08-12T09:41:22.881Z",   // eşzamanlılık damgası
  "baslik": { "belgeNo": "GNT2026000000056", "cariId": 318, ... },
  "satirlar": [ { "sira": 1, "stokId": 10248, "miktar": "40.00", ... } ],
  "hesaplananlar": { "araToplam": "1076190.48", "kdv": "210000.00", "genelToplam": "1260000.00" }
}
  • Eşzamanlılık: surum uyuşmazsa 409 Conflict + karşı tarafın değerleri döner. "Son kaydeden kazanır" yok.
  • Hesaplanan alanlar istemciden gelmez — sunucu hesaplar, yanıtta döner. İstemci yalnız gösterir.
  • Taslak kayıt ile kesinleşmiş kayıt farkı durum alanıyla; silme yalnız taslakta.
Kabul ölçütü: İki tarayıcıda aynı fatura açılıp ikisi de kaydedildiğinde ikincisi 409 alıyor ve kullanıcıya çakışan alanlar gösteriliyor.

3.3 Yetki sözleşmesi

GET /api/yetki/oturum   → oturum açılışında bir kez
{
  "kullanici": "AysD", "firmaId": 1, "subeId": 1, "subeler": [1,2,3],
  "roller": ["SATIS_YONETICI"],
  "yetkiler": { "FATURA.OKU":1, "FATURA.YAZ":1, "FATURA.SIL":0, "FATURA.GONDER":1, ... },
  "alanYetki": { "STOK.MALIYET": 0 }          // alan bazlı gizleme
}
  • İstemci yetkiyi yalnız görsel filtre için kullanır (menüde gösterme/gizleme).
  • Sunucu her çağrıda yeniden kontrol eder. İstemci filtresi güvenlik değildir.
  • Yetkisiz işlem menüde hiç görünmez; gri gösterip "yetkiniz yok" demek yok.
  • Alan bazlı yetki: maliyet/kâr gibi alanlar yanıttan çıkarılır, gizlenmez.

3.4 Hata formatı

Tek biçim — application/problem+json üzerine Gentegre alanları:

{
  "durum": 422,
  "kod": "FATURA.KDV_ORANI_GECERSIZ",
  "mesaj": "KDV oranı stok kartındaki oranla uyuşmuyor.",
  "detay": "STK.10248 için tanımlı oran %20, gelen %10.",
  "alan": "satirlar[0].kdvOrani",
  "izlemeNo": "7f3a1c94",                // log ile eşleşir
  "cozum": "Stok kartından oranı güncelleyin ya da satır oranını %20 yapın."
}
  • kod makine tarafından okunur ve sabittir — mesaj metni değişebilir, kod değişmez.
  • alan doluysa istemci ilgili giriş kutusuna odaklanır ve hatayı orada gösterir.
  • Beklenmeyen hata: 500 + yalnız izlemeNo. Yığın izi kullanıcıya gösterilmez.

3.9 Aksiyon kataloğu sözleşmesi

Tek kaynak, dört tüketici Her ekranın bir aksiyon kataloğu vardır. Araç çubuğu, sağ tuş menüsü, Ctrl+K komut paleti ve AI'ın izinli fonksiyon listesi bu katalogdan üretilir. Yeni bir işlem eklendiğinde dördü birden güncellenir. Bu yapı fatura ekranlarındaki prototiple doğrulandı. 
{
  id: 'fatura.gonder',
  ad: 'e-Fatura Gönder',  ikon: 'send',  kisayol: 'Ctrl+G',
  kapsam: ['satir','coklu'],          // satir | coklu | baslik | hucre | kalem | alan
  yetki:  'FATURA.GONDER',
  aiCagrilabilir: true,               // AI bu fonksiyonu çağırabilir mi
  aiOnayGerekir: true,                // çağırırsa taslak üretir, kullanıcı onaylar
  etiket: b => b.adet > 1 ? `${b.adet} faturayı gönder` : 'e-Fatura Gönder',
  aktif:  b => b.hepsiGonderilebilir ? true : 'Seçimde gönderilemeyecek belge var',
  calistir: b => api.post('/api/fatura/gonder', { idler: b.idler })
}
  • aktif true değilse sebebini döner — kullanıcı neden yapamadığını görür. Kuralı öğreten en ucuz yer burasıdır.
  • Yetkisiz aksiyon katalogdan tamamen düşer.
  • aiCagrilabilir işaretli aksiyonlar AI fonksiyon kataloğuna otomatik girer — ikinci bir liste tutulmaz.

3.10 AI fonksiyon sözleşmesi

POST /api/ai/sohbet
{ "soru": "bu ay geciken tahsilatlar kimde",
  "baglam": { "modul":"cari", "ekran":"cari_liste", "seciliId": 318, "sube": 1 },
  "sohbetId": "..." }

Yanıt akışı: metin → araç çağrısı → sonuç → metin → (varsa) onay kartı
{ "tip":"aracCagrisi", "fonksiyon":"cari_geciken_tahsilat",
  "parametre":{"sube":1,"gunSayisi":30}, "sure_ms":402 }
{ "tip":"onay", "aksiyon":"cari.hatirlatmaGonder", "taslak":{...},
  "aciklama":"14 cariye hatırlatma e-postası taslağı hazırlandı." }
  • Model doğrudan SQL çalıştırmaz. Yalnız katalogdaki aiCagrilabilir fonksiyonlar.
  • Firma/şube/kullanıcı filtresi API katmanında eklenir — modelin parametresine bırakılmaz.
  • Yazma işlemi daima onay tipi döndürür; kullanıcı onaylamadan hiçbir kayıt değişmez.
  • Her adım AILOG'a yazılır: prompt, fonksiyon, parametre, sonuç boyutu, token, maliyet, onay kararı.
  • Maliyet tavanı kullanıcı ve firma bazında; aşılırsa çağrı reddedilir.
Faz 0 sözleşme çıktısı: her sözleşme için bir OpenAPI parçası + bir örnek istek/yanıt + bir kabul testi. Onay alındıktan sonra kilitlenir; değişiklik yeni sürüm numarasıyla yapılır.

4.3 iframe kuralı

Üretimde iframe yok gentegre_v4_web.html ve diğer kabuklardaki iframe + postMessage yaklaşımı yalnız mockup galerisinin tekniğidir — 97 bağımsız HTML dosyasını tek kabukta gösterebilmek için. Üretimde her ekran bir React route ve component'tir: 
Mockup (bugün)                    Üretim (hedef)
kabuk → iframe stok_listesi.html   <Route path="/stok/kartlar"      element={<StokListe/>} />
kabuk → iframe cari_liste.html     <Route path="/cari/kartlar"      element={<CariListe/>} />
modal kart penceresi               <Route path="/stok/kartlar/:kod" element={<StokKart/>} />

Kart artık modal değil, kendi adresi olan sayfadır — geri tuşu, yer imi ve bağlantı paylaşımı çalışsın. Modal yalnız gerçek lookup diyalogları için (rehber_arama gibi).

6 Faz 1 — Dikey Dilim: Cari + Stok + Satış Faturası

Neden bu üçlü Değerlendirmenin en yerinde uyarısı: sadece Cari + Stok "liste ve kart yazdık" demektir, mimariyi sınamaz. Satış faturası eklendiğinde işin gerçeği devreye girer: çoklu tablo yazan tek transaction, belge numaralama, stok düşümü, cari hareket, döviz, yuvarlama, e-belge, döküm ve log — hepsi aynı anda.

6.1 Kapsanacak akış

Cari listesi → cari seç → Cari kartı (bakiye, risk)
                    ↓
Stok listesi → stok durumu (depo bazlı)
                    ↓
Yeni Satış Faturası
  → GenLookup ile cari seç
  → GenKalemGrid'de stok seç, miktar/fiyat/iskonto gir
  → sunucu hesaplar: ara toplam, iskonto, matrah, KDV, genel toplam
  → Kaydet  ⇒ TEK TRANSACTION:
       belge no üret · fatura başlık + satır yaz · stok hareketi yaz
       · stok durumu güncelle · cari hareket yaz · log yaz
  → Fatura dökümü (PDF)
  → e-Fatura gönder (kuyruk + durum sorgu)
  → Cari ekstresinde ve stok hareketlerinde görünür

7 SP Envanteri ve PostgreSQL Göçü

7.1 Envanter çıkarma (Faz 0 çıktısı)

-- MSSQL: tüm yordam ve fonksiyonlar, boyut ve bağımlılıkla
SELECT o.name, o.type_desc,
       LEN(m.definition)                       AS uzunluk,
       (SELECT COUNT(*) FROM sys.sql_expression_dependencies d
         WHERE d.referencing_id = o.object_id)  AS bagimlilik
FROM sys.sql_modules m
JOIN sys.objects o ON o.object_id = m.object_id
ORDER BY uzunluk DESC;

Çıktı bir tabloya dökülür ve her satıra çağıran ekran, iş kritikliği ve sınıf (P1/P2/P3) elle işlenir. Bu, tek seferlik ama atlanamaz bir analiz işidir.

7.2 Sınıflandırma kuralı

SınıfTanımNe yapılır
P1Faz 1 akışının çalışması için şart Faz 1 içinde taşınır. Yazma mantığı içeriyorsa C# servisine alınır, yalnız okuma ise PG fonksiyonu olur.
P2Diğer modüller için gerekli, iş kritik İlgili modülün fazında taşınır. Taşımadan önce mutabakat testi yazılır.
P3Nadir kullanılan, tek seferlik ya da ölü kod Kullanım logu ile doğrulanır; kullanılmıyorsa taşınmaz. Envanterin şaşırtıcı biçimde büyük kısmı buradadır.

İşNeredeGerekçe

7.4 Mutabakat testi

Her taşınan hesaplama için aynı girdiyle eski ve yeni sistemi çalıştırıp sonucu karşılaştıran otomatik test:

  • Mizan toplamları, cari bakiyeler, stok durumu, fatura toplamları
  • Fark toleransı 0,00; fark varsa test kırmızı
  • Gerçek müşteri verisinin anonimleştirilmiş kopyası üzerinde çalışır

10 Tamamlandı Tanımı (DoD)

Bir ekran "bitti" sayılması için:

  1. Liste ve kart sözleşmelere uygun; ekrana özel uç nokta yok
  2. Yetki üç rolle denendi; yetkisiz işlem sunucuda engelleniyor
  3. Aksiyon kataloğu tanımlı; araç çubuğu, sağ tuş ve komut paleti aynı kaynaktan üretiliyor
  4. Hatalar sözleşme biçiminde; kullanıcıya anlaşılır mesaj + izleme no
  5. Log yazılıyor (değişiklikte alan bazlı)
  6. Tutar içeren ekranda mutabakat testi yeşil
  7. Performans bütçesi (§11) sağlanıyor
  8. Telefon genişliğinde kullanılabilir
  9. Klavyeyle uçtan uca kullanılabilir (fare olmadan)
  10. DevExtreme import'u yalnız gen/ altında
  11. Playwright ile bir "mutlu yol" testi yazıldı
  12. Mockup ile karşılaştırıldı; bilinçli sapmalar not edildi
